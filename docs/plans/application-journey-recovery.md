# Application journey recovery

Reviewed checkpoint: `2febb8e813590c6f468bfa2503d35cba12b94ed1`, branch `feat/react-crossbrowser-integration`, draft PR #15. This plan is not approval to merge or release. Only this document is changed by this review.

## A. Verified current state and evidence limits

Source inspection establishes the following implementation, not native acceptance:

- `WorkspacePage.tsx` composes Job, Documents, Questions, Apply and Applied in one workspace. Hidden sections remain mounted, preserving disposable editor state. `WritingSection.tsx` polls visible questions and protects dirty drafts. The stale instruction directing Questions users into Apply has been removed.
- `OpportunitiesPage.tsx` and `opportunities/api.ts` expose single and bulk intake, including `/api/opportunities/import`. Bulk import explicitly saves URLs locally rather than claiming retrieval has completed. Supported-source search needs a separate reachability check: the inspected HTTP route registration contains no obvious job-search endpoint. Do not equate list filtering with source search or remove existing legacy entry points.
- `buildContinuation` in `workspace_continuation_api.go` checks selected résumé availability and bytes, selected letter identity, profile revision, live answers and browser ownership. `continuationContinueAPI` revalidates résumé and profile before dispatch, then composes résumé, contacts, letter and answers. Successful independent effects are not rolled back by another item's failure.
- `workspace_discovery_api.go:writingDiscoverAPI` reuses current saved inventory, otherwise invokes public Greenhouse discovery or isolated Ashby preview. It does not use the managed session host. Ordinary question GET remains read-only. `WorkspacePage` triggers this once on entering Documents or Questions. Failure is reported but the current page has no explicit discovery retry; navigating tabs intentionally does not repeatedly fetch. A transient failure therefore remains until workspace reload. This is a recovery limitation, not a reason to block Apply.
- `early_application_answers.go` preserves answers with discovery identity, destination and revision. `application_answer_reconciliation.go:reconcileEarlyAnswer` checks provider-specific field identity, unique occurrence, label, type, requiredness, options and sensitivity. These checks protect real properties; the separate acceptance ceremony is not itself needed for safe transfer.
- **Broken composition:** `summarizePreparation` in `application_continuation.go` uses live `ReadyAnswers()` only. `buildContinuation` reports early answers as awaiting reconciliation. React cannot authorize their conditional future transfer. `answerTransferForAction` validates only the live scope. `tryAnswers` appends the entire approved batch to attempted and clears it on its first pass. Simply adding early answers to that slice would incorrectly consume waiting answers.
- The watcher in `browser_session.go` observes every 750 ms, persists after two consistent observations, and calls resume/contact/letter/answer operations sequentially. Answer execution can occur before a new observation is persisted. Matching must therefore use current session-owned evidence and wait for a suitable observation, not assume the latest stored browser inspection describes this session.
- Chromium and Firefox use the shared Go session host and answer-transfer contract. Preserve their implementations; this defect lies in Go authorization and attempt lifecycle, not engine selection.
- `SubmissionSection.tsx` offers one completion action, mints the existing review token internally, reuses it on retry, and reads history after errors. `continuationSubmitAPI` delegates durable validation. Next fetches current browser status and warns before closure; `continuationNextAPI` does not require Applied. Preserve these paths.

Independent execution for this review: `go test ./...` passed (internal/app 15.049 seconds; several package results were cached). No browser or native GUI run was independently performed in this review. Previous reported browser passes are historical claims, not renewed evidence.

Relevant existing tests: `react_journey_qualification_test.go:TestReactJourneyDocumentTransfer`, `application_answer_preview_qualification_test.go:TestControlledAshbyPreviewIsReadOnlyAndSessionIsolated`, `workspace_discovery_api_test.go`, `application_answer_transfer_test.go`, `application_answer_reconciliation_test.go`, and `workspace_continuation_api_test.go`. The current React journey checks that an early answer is matched, but does not prove that this early answer fills under the original click. Its later live-answer transfer is a different capability. Its fixture factory maps a synthetic origin into the session host; it does not independently prove production launch dispatch.

## B. Journey-level findings

1. **P0: preparation stops at Apply.** Saved early answers are displayed as excluded instead of entering the explicit Fill scope. Fix scope and execution together; do not add an acceptance button.
2. **P0: delayed controls cannot be represented safely by the current batch lifecycle.** Waiting is conflated with attempted. A bounded extension of `applicationAnswerTransfer` is sufficient; no workflow engine is justified.
3. **P1: qualification can pass while the required journey fails.** The existing fixture opens View before the relevant Fill and proves matching without transfer of the early draft. Replace that main scenario with fresh-session one-click filling. Retain View's no-transfer check as a separate scenario.
4. **P1: CI does not protect this branch's outcome.** `.github/workflows/ci.yml` triggers PRs only to main, whereas PR #15 targets the journey branch. It runs ordinary and desktop Go tests but not opt-in qualification-tag browser tests. Building a bundle is not applicant-journey evidence.
5. **P2: transient early discovery has no in-place retry.** Add a small retry only on failure, retaining saved answers and dirty editor contents. Do not rediscover automatically on each render.
6. **Unresolved contract coverage:** source-search reachability and complete native intake-to-next navigation have not been demonstrated. Establish the actual existing entry point before proposing implementation. Do not invent a provider or broaden ATS scope.

## C. Target behavior

Applicant adds/selects a job, chooses a résumé and optional letter in Documents, and prepares discovered questions in Questions. Background discovery sends no applicant material. Apply shows exact saved material, including early answers labelled “fills when the same question is found.” View opens/returns without transfer. Fill captures one immutable authorization, opens/reuses the owned session, and fills only qualified material. Late matching uses that same authorization; edits or newly created answers require another click. Existing employer values remain untouched. Missing/changed/ambiguous controls produce understandable attention outcomes without losing drafts. The applicant submits personally, records completion once, and moves on; moving on without submission never records Applied.

## D. Implementation slices

### 1. Complete conditional early-answer filling (first and highest value)

Deliver the complete Questions → fresh Fill → actual employer value path. Reuse `reconcileEarlyAnswer`, `validateApplicationAnswerValue`, existing session `FillAnswer`, attempted tracking and current Go command composition.

Changes:
- Build one Go-owned displayed answer scope containing eligible live answers and exact saved early identities, revisions, values and discovery fingerprints. Exclude sensitive/unsupported drafts. Keep optional material exclusion behavior. Bind the authorization hash to revision and identity, not just text; retain legacy hash behavior where required by legacy endpoints.
- Validate and capture the selected scope **before browser launch or other effects**. Do not rebuild authorization from newer saved material after launch. An explicit live saved answer, including a deliberate clear, takes precedence over an older early draft; never silently substitute an undisplayed answer.
- Extend the existing transfer object with pending early snapshots and per-item terminal/attempted tracking. Do not promote drafts into durable live answers merely to fill them. This avoids a new persisted writer and removes the need for acceptance ceremony.
- On each current owned observation, revalidate destination, active job, exact early revision/identity/value and current discovery. Match against evidence from the current session. Reuse the matcher and normal answer validator. Check saved live-answer precedence again immediately before dispatch. Changed revision, ambiguity, changed question, unsupported/sensitive control or conflicting live answer yields a terminal manual outcome; no write.
- Absence while the page loads remains pending. Distinguish partial absence from a complete incompatible form. Show “not found on this page; complete manually if needed” for unavailable controls while retaining only never-attempted conditional eligibility during the same session. Do not block authorization of other newly prepared material merely because an old item remains pending.
- Mark dispatch as attempted before external mutation. A returned uncertainty, interruption or error after dispatch is terminal and never replayed. Preserve terminal identities across subsequent authorizations within the session. Pending items cease on close/restart and cannot carry authority into a replacement session.
- Preserve resume no-replay behavior; a later answer-only Fill must not arm résumé upload again. Do not change browser drivers unless a controlled failure proves it necessary.

#### Fresh-session eligibility and command ordering

Trace: `buildContinuation` → `summarizePreparation` → React `prep.includeAnswers` initializes `wantAnswers` → `runAuthorize` posts `include_answers` and `answerReviewHash` → `continuationContinueAPI` dispatches résumé before `answerTransferForAction`. Today the scope originates only from live `ReadyAnswers()`, so early-only preparation makes the answer checkbox absent/disabled and posts `include_answers=false`, even though the résumé enables Fill. Fix the scope producer and consumer together.

With a valid selected résumé, no managed session, no live inspection, and only saved early answers: return those answers in `pendingAnswers`, indicate conditional matching in their source/status, set `includeAnswers=true`, and use the existing initial selection behavior to preselect them. Preserve deliberate exclusions; do not require another checkbox or View action. The Fill button must remain enabled under the existing résumé requirement. Capture and validate the displayed combined scope at the start of the POST, before launching the browser. Pass that immutable snapshot to the answer arming path after successful session launch/watch registration; do not rerun the old live-only hash calculation after launch. The existing `armAnswers` session requirement remains valid at arming time, not as a prerequisite for displaying or authorizing early answers. Launch failure must report failure and must not retain authorization for a later unrelated session. Keep legacy live-only endpoints compatible. A subsequent answer-only Fill reuses the session without rearming résumé upload.

#### Multi-step waiting and terminal outcomes

A missing field is **not** a terminal mismatch merely because the current page is rendered or an inspection says `rendered_complete`: that does not establish completion of all employer steps. Keep never-attempted authorized items pending across owned page/step changes for the lifetime of the same session. Re-evaluate on subsequent observations, including after the watcher persists a new inventory. Display a nonblocking “not on this page; waiting for a matching question” outcome. A timeout may change this explanatory message but cannot manufacture an attempted write or silently revoke eligibility for a later step.

Terminal no-write outcomes require affirmative disqualification: changed authorized revision/destination, conflicting saved live record, ambiguous identity, changed control definition, sensitivity or unsupported type. Distinguish these from absence. Once the exact qualified field is dispatched, retain its attempted identity before calling the filler; successful, already-present and uncertain outcomes are not pending and must never be dispatched again by background observation. An error with uncertain dispatch is terminal. Close/restart cancels pending authority. Keep pending and terminal item records within the existing transfer structure; do not let batch-level `waiting` prevent a new explicit scope from adding other answers, replace outstanding authorization, or replay terminal items. Test initial empty page → page one without the field → page two with the field: one original click, one write. Separately test uncertain write → page change → same field: zero retries.

#### Saved live answers, including deliberate clears

Use `savedLiveAnswer(job, matched.LiveQuestionKey)` (destination/provider/key scoped), not `ReadyAnswers()`, to determine precedence. `ReadyAnswers()` deliberately filters empty values and therefore cannot distinguish absence from an intentional clear. Only `sql.ErrNoRows` means no saved live decision; any existing live record, even `Value == ""`, blocks fallback from an early draft. Database errors must fail closed. This conservative precedence avoids comparing unrelated early and live revision counters.

Check precedence when constructing a matchable displayed scope and again immediately before dispatch after a delayed match. If a live answer is created, edited or cleared after the click, suppress the early item with a no-write outcome; do not substitute the new live text under old authorization. A live answer may transfer only if independently present in the captured displayed scope and its own revision/value remain current. Do not delete or overwrite live records, and do not persist an early draft into the live store to bypass precedence. Test both a preexisting cleared record and a clear occurring between authorization and delayed control appearance; neither may resurrect the early answer. Preserve the legacy acceptance handler as an explicit legacy operation, not an automatic step in React.

Acceptance: extend the existing React journey for both engines. Discover Ashby early, save answer, never click View, click Fill once, delay the matching field until after authorization, read exact answer and PDF bytes and contact values. Count field events/uploads/submissions. Independently test changed/ambiguous match, newer or cleared live answer, post-click early edit, preserved manual employer value and uncertainty without replay. Verify one successful early answer is not withheld because another is unsafe. Preserve Greenhouse matching tests and add the same authorization path with controlled definitions. Dependency: none. Out of scope: new states persisted in SQLite, settings, engines, provider expansion, packaging, generic orchestration.
