# Application workflow Checkpoint 1: diagnosis and qualification

Initial repository state was clean on `main` at `903c34a55be16c73ceaf86403a482fe248e3423f`; read-only `origin/main` matched. Diagnosis used the current implementation, isolated SQLite/resume fixtures, server-rendered pages, and controlled local Chromium.

## Diagnosis

| Operation | Expected behavior | Reproduced result | Root cause | Corrective action |
|---|---|---|---|---|
| Record completion | Confirm the applicant's prior employer submission, commit one row, show Applied and History, then allow Next job. | The rendered Wails-compatible form successfully reached SQLite and History in baseline Chromium. A stale review and a simulated transaction failure both redirected back, but optional notes disappeared. | The record form kept notes only in the document. The redirect discarded that document state; no local recovery copy existed. The core review-token, resume-integrity, transaction, and redirect path did not fail in the controlled run. | Keep the optional note in tab-local `sessionStorage` when the user submits the confirmation form; restore it after stale or failed recording; clear it after History shows success. Keep server-side resume review and idempotency checks. |
| Save and transfer answers | Save against the current observed question, display exact eligible transfer scope, require a separate fill action, preserve existing values, and show field-level results. | Stable observed narrative/select/checkbox/radio answers saved and reached the controlled employer form. Manual and ambiguous values were preserved. The visible status still said `complete` for mixed outcomes, and `correct` was labeled as if it had been filled. A post-save employer field identity change correctly made the old answer non-current. | Transfer processing completion was surfaced as if it meant every answer had been filled. The presentation grouped `filled` and `correct` under one claim and did not summarize manual or uncertain results. | Keep processing completion separate from per-field results. Show counts for filled, already correct, manual, and uncertain; open the result list on completion; label each outcome precisely. Show locally saved answers as local until transfer authorization. Keep an old answer for review if the observed field identity changes. |
| AI draft answer | Select current reviewed evidence or a deliberately selected resume excerpt, inspect the exact source payload, authorize one generation, preview, adopt explicitly, and save normally. | The fake-provider browser journey worked through preview, adoption, local save, refresh, cancellation, and failure paths. Before the fix, rendered controls selected Ollama but left the required model blank. | The model field had no provider default or readiness guidance. A user without Career Evidence also had no clear explanation that a selected resume excerpt was an alternative. | Initialize provider/model from existing provider defaults, preserve per-provider model choices locally, explain provider setup and availability, and make the resume-evidence alternative explicit. Do not relax the observed-question eligibility rule or reuse consent. |

The report does not identify the user's exact employer fields or AI question. Therefore the controlled transfer succeeded for supported current fields, and the AI generation failure itself was not reproducible without a live paid provider. Unsupported, ambiguous, and changed question identities remain manual or review-only. AI drafting still requires a supported narrative question observed in the managed browser.

## Controlled evidence

- `TestControlledSubmissionRecordingWorkflow` drove the rendered form at 1100×800 and 700×550, including keyboard confirmation, cancellation with both dirty answer and cover-letter editors, Wails-compatible POST redirect, no-JavaScript recording, stale resume recovery, SQLite transaction failure, retry, History, and Next job. After cancellation it verified both unsaved editors and notes remained present; after explicit confirmation it verified the saved letter stayed unchanged.
- `TestControlledCombinedContinuation` used a synthetic employer form and fake AI generator. It saved a manual answer and an AI answer, authorized transfer, checked employer field values, changed a captured field identity and confirmed the old answer stayed review-only, preserved a manually entered employer value, showed `5 filled and verified; 1 needs manual completion`, recorded one Applied row through the rendered YourMove form, and advanced to the next opportunity. Employer submission events remained zero.
- `TestControlledNarrativeAnswerWorkbench` checked exact source review, no provider call before consent, one call after explicit authorization, read-only preview, adoption as unsaved text, save and restart persistence, provider/model invalidation, timeout, cancellation, stale evidence, output failure, dirty editor preservation, and no-JavaScript local saving. Its generator was injected; no paid provider request was made.
- `TestControlledRuntimeRestart` started and restarted the ordinary executable with a sanitized, isolated `YOURMOVE_DATA_DIR`; synthetic jobs, resume, candidate profile, answer, and submission persisted. The test used a unique temporary screenshot directory.

## Data isolation

Controlled tests use `testWorkspace` temporary databases and resume directories. Qualification guards canonicalize SQLite and resume paths before browser startup. Runtime qualification removes any inherited `YOURMOVE_DATA_DIR` before setting its own temporary directory. No normal YourMove database, real resume, candidate profile, answer, or submission history was used or modified.
