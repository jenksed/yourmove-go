# v0.2.0 macOS automatic updates — execution contract

**Status:** Isolated preparation on `v0.2/feat-macos-updater`. Not integrated, shipped or verified on an installed Mac. This document is linked from the existing [v0.2 roadmap](../ROADMAP.md) and [release process](../RELEASE_PROCESS.md); it is not a replacement for the locally maintained `docs/planning/v0.2-engineering-plan.md`. Incorporate this outcome in that authoritative plan during integration rather than creating a parallel roadmap.

## Outcome and boundary

An existing **updater-enabled** Apple Silicon YourMove installation checks for newer production versions without blocking local work, shows version/release notes, and lets the user approve download, authenticated installation and restart. Upgrading retains the complete applicant workspace (SQLite and sidecars, stored résumé bytes, saved answers/letters, Career Evidence, selections/settings and history). An update failure leaves a usable current app and manual DMG path.

Existing v0.1.0 builds do **not** have update code. They require one manual DMG upgrade to an updater-enabled release. Do not imply otherwise. No Windows/Linux updater or auto-submit capability is in this workstream.

## Incremental implementation

### U1a — Release-compatible update archive (parallel-safe, started)

Use `release/macos/package-update.sh` to consume an **already Developer ID-signed, notarized** `YourMove.app`. Verify bundle ID, version/build, arm64 architecture, signed identity, stapled ticket and Gatekeeper assessment. Create `YourMove-<version>-darwin-arm64-update.zip` containing exactly one top-level `YourMove.app`, extract and verify it again, and generate `SHA256SUMS.update`.

The script never publishes, signs/notarizes or installs. On macOS, test rejection of ad-hoc candidate and acceptance of a real signed/notarized candidate. The resulting ZIP alone is **not yet a fully authenticated update**: signature must be attached through a signed manifest validated with the key pinned in the installed app.

### U1b — Installed-app discovery and review (requires accepted S4 host)

Initialize `app.Updater` for signed, macOS arm64 production builds only. Use an actual `CurrentVersion` from the same release metadata as Info.plist; keep development runs from checking production channels accidentally. Use Wails' `updater/providers/endpoint` with a static **signed Wails update manifest** delivered through the owner-controlled GitHub Release channel. Pin a public verification key in the application; the private signing key must remain outside source and be handled only by the authorized signing operator. Prefer Wails' default update window; keep release notes and install/restart actions explicit.

Provide an on-demand “Check for Updates” action and a nonblocking startup/periodic check that notifies only when newer. Do not auto-download, auto-quit or auto-install without the user's explicit action. Keep failure localized so offline job management works. Preserve the Wails HTTP/asset host and native window. Do not add new SQLite schema, React architecture or custom swap logic.

### U1c — Authenticated release artifact and update flow (owner-controlled signing)

Have the existing macOS release pipeline build a versioned `.app`, sign with Developer ID, notarize and staple it, package updater ZIP plus existing DMG/manual fallback, and produce corresponding source archive/checksums. Use the pinned Wails CLI to create/sign and verify an update manifest naming the **exact** ZIP SHA/version/arch and pointing to a specific GitHub Release download URL. Require a production-suitable signature; digest-only GitHub SHA256SUMS is not enough. Keep update archive and signed manifest in the same owner-approved GitHub Release, with a stable manifest lookup convention; never use an installer DMG as the updater artifact.

Nothing in U1a authorizes a real Apple upload, key generation/rotation, manifest publication, new GitHub Release or changing live download links. Owner approval remains required.

### U1d — Real installed upgrade and preservation acceptance

With an isolated synthetic applicant workspace, install updater-enabled candidate A normally, create opportunities, import distinct résumé revisions, save answers/letters/evidence and associations, capture IDs and file hashes. Serve a separately authenticated later candidate B through a controlled update channel; demonstrate nonblocking discovery, accurate version/release notes, explicit approve, verified staging, restart and installed version B, then compare IDs/bytes/associations/history/settings. Repeat with update network/checksum/signature failure and an unwritable target; confirm current application remains usable and manual DMG update works. Test normal `/Applications` and per-user installation permissions as relevant. A unit test or binary compilation is not proof.

Broader v0.2 data integrity gates still govern upgrades after S2 and S3 are integrated. No installer, new platform or release approval is implied by isolated U1 verification.
