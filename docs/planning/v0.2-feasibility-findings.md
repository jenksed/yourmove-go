## 1. Executive verdict

**GO WITH CONSTRAINTS.**

The existing Go/Wails architecture is a viable foundation for Windows 11 x64 and Ubuntu 24.04 x64. No rewrite, no framework migration, and no platform-abstraction layer is indicated. The evidence:

- The entire non-desktop Go tree — HTTP routes, SQLite persistence (`modernc.org/sqlite`, pure Go, no CGO), embedded React frontend — **cross-compiles cleanly for `windows/amd64` and `linux/amd64`** (VERIFIED).
- The exact Wails API surface YourMove uses (`application.New`, `AssetOptions{Handler}`, `WebviewWindowOptions`, `Dialog.OpenFile/SaveFileWithOptions`, `Browser.OpenURL`) **compiles unchanged against Wails v3.0.0 and v3.1.0 on darwin/arm64, and a same-shape Wails app compiles for windows/amd64 with `CGO_ENABLED=0`** (VERIFIED).
- The native macOS app **launches and creates its `YourMove` window** on the pinned beta (VERIFIED), and the full save → edit → `kill -9` → reopen persistence journey **passes against the shared storage layer** (VERIFIED).
- The Wails v3.1.0 toolchain already contains the packaging primitives both new platforms need (**NSIS installer build support with WebView2 control; `deb`/`rpm`/`appimage` Linux targets**) (VERIFIED by module-source inspection).

Constraints that make this "with constraints" rather than unqualified GO:

1. **No Windows or Ubuntu graphical environment was available.** Native launch, WebView rendering, dialogs, managed-browser startup, and installers on the two new platforms are all **NOT RUN**. Nothing in this report upgrades a compile check into a qualification claim.
2. **Upgrade Wails beta.32 → v3.1.0 before platform work.** Beta.32 predates two Windows crash fixes (v3.0.0) and a WebView2 request-body fix (v3.1.0, PR #6326) that sits directly on YourMove's form-POST path. API compatibility is verified; the bump is small.
3. **Chromium/Node discovery is Unix/macOS-only today.** Two `isExecutableFile` helpers reject every Windows `.exe` by construction, and all search paths/suffixes are macOS layouts. This is the one concrete code-level blocker for employer-browser work on Windows, and it is small and bounded.
4. The approved specs A and B named in the mission brief **were not present in this worktree** (no `*DRAFT*` planning documents found). Findings are anchored to the closest authoritative in-repo sources instead (§2). Acceptance mapping to N01–N12/G1–G7 therefore cannot be completed here and must be re-checked against the specs before implementation.

No demonstrated blocker to *beginning* v0.2.0 development was found. The blockers that exist are to *claiming* Windows/Ubuntu support, which is implementation and qualification work, not feasibility work.

## 3. Wails/Go compatibility decision

**Recommendation: upgrade to Wails v3.1.0 (exact pin) and Go 1.27.3, then run both CI jobs plus a macOS desktop smoke before any platform work.**

Evidence:

- **API compatibility VERIFIED.** A shim mirroring `desktop.go`'s exact Wails usage compiled clean on `darwin/arm64` against both v3.0.0 and v3.1.0 (only pre-existing macOS deployment-target linker warnings). `dialogs.go` API (`PromptForSingleSelection`, `SaveFileDialogOptions`) is identical between beta.32 and v3.0.0 by file diff.
- **Decisive trade-off.** Staying on beta.32 means shipping known-fixed Windows defects: menu-bar `SetTextColor` panic (#6311) and `uxtheme.dll` crash (#6358) fixed in v3.0.0, and **WebView2 dropping request bodies when `Content-Length` is omitted (#6326), fixed in v3.1.0** — the latter sits directly on YourMove's URL-encoded/multipart form-POST path through the custom asset handler. Linux gains the cross-origin child-frame IPC guard (GHSA-r5j2-ghh9-2jqw mitigation) and dark-mode/zoom correctness fixes. Cost of the upgrade is a `go.mod` bump + `go mod tidy` + test suite; no application code changes were indicated by the compile probes.
- **Do not chase v3.2.0 nightlies.** The nightlies advertise experimental CGO-free macOS/Linux backends — interesting for future build simplification, but nightly, experimental, and unnecessary for feasibility.
- **Go 1.27.2 → 1.27.3** is a patch-level bump (stable per go.dev). Adopt and let CI confirm; Wails v3.1.0 itself only requires Go ≥ 1.26.
- **Deferred, not decided:** whether to adopt Wails' `wake`-based YAML packaging tasks vs. extending the existing `release/macos/*.sh` style per platform. That is an implementation choice, not a feasibility dependency.

Bounded upgrade procedure: bump `go.mod`, `go mod tidy`, `go test ./...`, `go test -tags desktop ./...`, rebuild macOS bundle via `release/macos/build.sh`, 15-second native launch check (§4). Back out if any step regresses.

## 5. Necessary implementation changes

Smallest credible set. File references are to the current tree.

### 5.1 Native startup and persistence (both new platforms)

1. **Add platform desktop entry points.** `desktop.go` (`//go:build desktop && darwin`) and `desktop_probe.go` (`desktop && darwin`) exclude all other OSes. Add `desktop_windows.go` (`desktop && windows`) and `desktop_linux.go` (`desktop && linux`) reusing the same `app.New` composition; generalize `desktop_probe.go` tags. Estimated small — the composition is already platform-neutral.
2. **Adopt Wails v3.1.0 + Go 1.27.3** (§3). Re-run both CI jobs and the macOS launch check.
3. **Re-observe the POST/redirect shim per WebView.** `internal/app/desktop_redirect.go` + `withWailsOrigin` were built for WKWebView quirks. Keep the allowlist approach (it is URL-shape-based and portable), but verify each POST destination on WebView2 and WebKitGTK; extend only on observed failure. The v3.1.0 WebView2 body fix removes one known failure class.
4. **Confirm storage-permission behavior on Windows.** `internal/storage/paths.go` `Chmod(0700)` — verify no error on ACL-based filesystems during the first native run; adjust to tolerate (not weaken) Windows semantics if needed. No schema or migration changes indicated.
5. **Build matrix first, GUI second.** Add `GOOS=windows` / `GOOS=linux` compile checks to CI immediately (cheap, runs anywhere); native GUI runs stay on platform runners/hosts.

### 5.2 Browser-assisted application preparation (both new platforms)

6. **Fix executable validation for Windows.** Replace/augment `isExecutableFile` in `internal/application/browser/chromium/executable.go` **and** `internal/application/browser/playwright/rpc.go` (duplicated logic) with an OS-aware check: on Windows accept regular `.exe` files (existence + extension + non-dir) instead of Unix exec bits. Add a shared helper — the duplication is the reason this must be one change, not two.
7. **Add Windows + Linux discovery paths.** Chromium: `%ProgramFiles%`/`%ProgramFiles(x86)%` Chrome locations, `chrome.exe` `LookPath` handling, `chrome-win64/chrome.exe` + `chrome-linux/chrome` Playwright suffixes, `%LOCALAPPDATA%/ms-playwright` root. Playwright `engines.go`: `chrome-win64`, `chrome-linux`, firefox `firefox.exe` variants. Linux: `/usr/bin`, `/opt/google/chrome/chrome` (snap explicitly out of scope until confinement is assessed).
8. **Per-platform browser-bundle layout.** `internal/application/browser/bundle.go` is macOS-`.app`-specific (Info.plist detection, macOS arm64 Node binary). Windows/Linux distribution needs the equivalent: install-adjacent `playwright-bridge/` + platform Node binary + `ms-playwright/` cache, with `BridgeReady()` honest per platform when pieces are missing. Check `scripts/setup-playwright-bridge.sh` assumptions for the new hosts.
9. **No changes indicated** to session ownership (`browser_session.go`), CDP transport, launch-arg shape, authorization model, or the no-automatic-submission rule. `kill_windows.go`/`kill_unix.go` already split process-group handling.

### 5.3 Native installers and qualified distribution

10. **Windows (NSIS, preferred).** Drive from Wails v3.1.0 `installerbuild` (NSIS compiler boundary) or the wake pipeline. Still required: installer identity + version, WebView2 prerequisite story (bundle vs. Evergreen bootstrapper — `WAILS_SKIP_WEBVIEW2` control exists), per-user install scope with `%APPDATA%` data preservation across upgrade, uninstall that **keeps** the workspace, and a signing/SmartScreen plan (certificate procurement is the long-lead item).
11. **Ubuntu (`deb`, preferred).** Drive from the wake pipeline's `deb` target. Still required: package name, `Depends: libwebkit2gtk-4.1-0` (runtime, not `-dev`), desktop entry + icon, postinst that does not touch `~/.config/YourMove`, and an upgrade test proving data preservation. Qualify on a clean 24.04 install, then record `$XDG_SESSION_TYPE` and qualify the other session type.
12. **macOS unchanged.** `release/macos/build.sh` stays; do not rework it for symmetry.

Explicitly **not** required: rewriting `internal/app`, a platform-adapter framework, frontend replacement, ATS expansion, cloud/sync, or CI redesign. Optional polish (icon variants, auto-update) is out of scope until qualified installs exist.

## 6. Dependency-aware implementation sequence

**Shared decisions first (block everything else):** Wails v3.1.0 + Go 1.27.3 adoption → CI compile matrix (`windows/amd64`, `linux/amd64` build checks) → executable-validation + discovery-path fixes (one change serving both platforms) → desktop entry-point files.

**First end-to-end platform slice (per platform):** native window launch → open Opportunities → save synthetic opportunity → quit → relaunch → state confirmed. This is the mission's success condition and the smallest slice that proves more than compilation. Do it on **Windows first**: the Wails/Windows backend compiles CGO-free (any CI runner can build it), WebView2 is inbox on Win11, and NSIS tooling is in-tree — the path from "builds" to "runs" has fewer host dependencies than Linux's GTK dev environment.

**Next capability the slice enables:** native dialogs (open/save/export) on the same slice, then managed-browser discovery against a real Chrome install, then controlled transfer on a fixture, then installer, then clean-host qualification.

**Parallel-safe work:** once shared decisions land, Windows and Ubuntu tracks are independent (different entry files, different discovery paths, different installers, different hosts). Never let two tracks edit `go.mod`/`go.sum`/shared discovery helpers simultaneously — serialize through the shared-decisions step above. macOS regression checks (`go test -tags desktop`, bundle build, 15-second launch) run alongside every platform increment.

What this sequence deliberately omits: an exhaustive backlog. Each step states its own exit evidence (a command, a window, a persisted row).

## 9. Final engineering recommendation

- **Ready to begin cross-platform implementation?** Yes — with the constraints in §1. Start with shared decisions (§6), not with platform installers.
- **Which platform first?** **Windows 11 x64**, on evidence: CGO-free Wails compilation proven from here, WebView2 inbox, NSIS support in-toolchain, and a smaller host-dependency chain to the first native run. Ubuntu follows with its native build host; macOS qualifies every step as the regression baseline.
- **Which versions?** **Wails v3.1.0 (exact pin), Go 1.27.3** — API-compatible (compiled), fixes Windows defects on YourMove's exact paths, no application rewrites indicated.
- **First implementation slice?** Shared version bump + CI compile matrix → `desktop && windows` entry + Windows discovery fixes → native save/restart slice on a real Win11 host. Then repeat the slice pattern for Ubuntu.
- **Evidence still required before any public platform claim:** on each new platform, at minimum — real native launch with window, WebView-rendered Opportunities, save/restart persistence on the platform data dir, native dialog open/save/cancel, managed-browser launch against real Chrome, one controlled fixture transfer with explicit authorization, installer install/upgrade-with-data-preserved on a clean host, and a re-check against specs A/B (G1–G7, N01–N12). A build log is not a qualification; this investigation deliberately stops before claiming any of it.
